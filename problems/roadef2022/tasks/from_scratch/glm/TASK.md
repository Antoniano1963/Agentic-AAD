# ROADEF2022: Designing and Implementing a Solver from Scratch

> **Translation note:** This file is an English translation of the original Chinese task instruction provided to the LLM agent during the experiments.

## 1. Task
You are the GLM Coding Agent. Implement a complete solver for the ROADEF2022 truck loading problem from scratch, and continuously optimize it based on training feedback. Independently understand the constraints, parse the data, design data structures and algorithms, generate outputs, debug, and pass the official checker. This task does not provide any off-the-shelf solver source code, seed algorithms, or reference solutions; the algorithmic direction is entirely up to you.
Sole working directory: `/data/CodeEvo/ROADEF2022/agent_runs/from_scratch/GLM_run01`. All development, compilation, temporary files, logs, and outputs must be placed inside it. You are permitted to use system tools, general-purpose libraries, and the provided open-source HiGHS; if using mathematical programming, you must design the formulation yourself. You must not invoke commercial optimizers or external solving services, and must not search for, download, or read existing solvers for this problem, other agents' artifacts, public solution files, or other experiment directories. You may consult general language and library documentation, and should record external dependencies and references.
First read the task instructions and official materials, briefly restate the configuration, and then begin development directly without waiting for further confirmation.

## 2. Provided Materials
- `initial_materials/problem.pdf`: official problem specification, constraints, and input/output formats; `initial_materials/rules.pdf`: competition rules. The experimental budget is governed by TASK.md.
- `initial_materials/checker/`: official CheckerChallenge-1.11.4.jar and instructions.
- `initial_materials/data/train/<instance>/`: the full set C of 50 training instances.
- `runtime/python_deps/`: general-purpose dependencies such as HiGHS and NumPy; `runtime/java/`: checker runtime. Contains no problem-specific models or solving code.
- `TRAIN_MANIFEST.json`: training file hashes and per-instance budgets.
- `REFERENCE_C.json`: fixed official final-phase per-instance best objective values, for evaluation only; contains no solutions or existing algorithm scores.
- `CPU_GROUPS.json`: 25 non-overlapping CPU affinity groups.
- `tools/INTERFACE.md`: candidate execution, build, and development check interface; `tools/evaluate_train.py`: unified evaluator; `tools/java.sh`: Java launch entry point. None of the above contains solving algorithms.
- `src/`, `candidates/`: initially empty, for you to implement and freeze candidates.
You must not modify the training inputs, reference values, checker, CPU groups, or evaluation protocol; write permission on the filesystem does not imply permission under the protocol.

## 3. Experimental Setup
Training set C50, 50 full training evaluation rounds, 50 solves per round; each instance is run only once per round, without three additional repetitions. All 50 rounds must be completed, without terminating early upon hitting a plateau; re-evaluations may be counted, but must be explicitly marked as re-evaluations and must not be described as new candidates or new progress.
25 original long-budget instances at 1500 seconds each, and 25 original short-budget instances at 900 seconds each. In each round, first run the 25 long-budget instances in parallel; only after that entire batch completes, run the 25 short-budget instances in parallel; rounds must not overlap. Unused time is not transferred to other instances.
At most 8 logical CPUs per instance (4 physical cores and their SMT threads) summed across all child processes; bind according to CPU_GROUPS, without expanding affinity. Total RSS across all child processes of a single instance is capped at 30,000,000,000 bytes (30 GB, not 30 GiB). Up to 200 logical CPUs across 25 parallel jobs; the server has approximately 750 GB of available memory—leave system headroom and do not exhaust memory by targeting the sum of per-task caps.
External timing runs from candidate launch to output completion, including parsing, search, sub-solves, and writing to disk. The internal search budget passed by the unified entry point to the candidate is the external limit minus 40 seconds. The candidate must exit within the hard wall-clock budget; the unified entry point will clean up the solve's process group upon timeout. The checker runs independently and its time is recorded separately, not counting against the candidate's search budget. Your run.sh should return 0 after completing normally and writing out the solution.
Fixed invocation parameter `seed=1111`. If any randomized mechanism is used, this parameter must actually be used and recorded; repeated rounds with the same seed cannot be called an independent random-seed experiment. Each solve starts independently, without warm-starting from prior solutions or search states, and without hardcoding solutions by instance filename.

## 4. Evaluation, Accounting, and Selection
Entry point: `python3 tools/evaluate_train.py --candidate candidates/v001 --round 1`. Place the complete candidate (source code, compiled binaries, build.sh, run.sh) into an independent candidate directory before invoking the entry point; see tools/INTERFACE.md for the candidate interface. The entry point freezes the candidate, generates per-instance files, and logs accounting records. Because runs take a long time, launch in the background and monitor existing logs rather than resubmitting due to SSH wait timeouts. Keep any candidate currently under evaluation unchanged.
Every started formal full evaluation counts as one round; crashes, infeasible solutions, and timeouts are all retained in the ledger without deleting, overwriting, or renumbering. Compilation is performed prior to calling the formal entry point; pure compilation failures do not consume rounds. The entry point uses a mutex lock to prevent concurrent rounds and uses unique round directories and a ledger to enforce the 50-round maximum; these are protocol safeguards, not tamper-proof security boundaries against an agent with write access to the directory.
Development smoke tests are allowed, but must log the candidate, instance, time budget, run count, CPU/wall-clock time, and result in dev/ledger.jsonl. Do not run off-ledger full-batch evaluations or screen large numbers of candidates in disguise to circumvent the 50-round budget.
Feasibility is determined by the official checker. The main report lists per-round feasible count / 50, per-instance objective values, timeouts, and resource anomalies. gap_i=(cost_i/reference_i-1)*100%; report the full training-set mean gap only when all 50 instances are feasible and resource-compliant; for partial feasibility, report only subset results with the instance set explicitly specified. For final selection, prioritize fully feasible candidates, then select the one with the lowest full training-set mean gap. Do not stitch together a candidate from per-instance historical bests; do not report the best observed across rounds as the performance of a single program. Each round performs a single solve per instance, so there is no mean/best distinction within a round.
Final evaluation is conducted by the researchers; do not obtain or evaluate any hidden data yourself, and do not alter the experimental scope.

## 5. Monitoring and Deliverables
External out-of-account resource monitoring is enabled, recording all activity of this UID (including development, compilation, solving, and checking) and inspecting solve process groups declared through the entry point. Monitoring only records and does not actively intervene; no cgroup CPU/memory hard isolation is provided. Sampling may miss short-lived processes and transient peaks, and summed RSS may double-count shared pages. The unified entry point sets CPU affinity and a wall-clock watchdog; memory constraints still require self-discipline and are subject to external logs. "No alerts" cannot be treated as complete proof of compliance.
Retain the full 50-round ledger, frozen candidate snapshots, per-instance outputs / checker logs / resource records, convergence.csv, DECISIONS.md, final REPORT.md, the rebuildable best candidate, and build instructions. Distinguish between new algorithmic changes and re-evaluations, and between observed facts and inferences; do not exaggerate improvements or conceal failures.
The current environment setup validation is placed in setup_validation/ and does not count toward your 50 formal rounds. Read all materials before starting, verify the entry point and configuration, and then begin the experiments.
